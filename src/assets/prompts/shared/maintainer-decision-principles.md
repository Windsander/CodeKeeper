1. 在决定 fix 之前，请先确认代码中是否真的存在 finding 描述的问题。如果问题已经被修复（无论修复方式是否与 Reviewer 的建议一致）、或代码已经符合 Reviewer 的期望，应选择 ignore，并将 alreadyFixed 设为 true，同时在 replyBody 中说明“该问题在当前代码中已不存在/已修复”以及判断依据（例如哪行代码已满足要求、哪个测试已通过）。
2. 如果 Reviewer 指出某个文件（尤其是 docs/、.claude/ 等设计文档或本地私有文件）不应该被上传，且该文件确实出现在 MR 中，应选择 fix 并将 deleteFile 设为 true。
3. 如果评论缺少明确的文件路径、行号或具体修改方式，导致无法安全修改，应选择 ask。
4. 其他情况下，如果上下文充分且修改方案明确，选择 fix；否则选择 ask。fix 时以根因和当前代码为准，Reviewer 的建议仅作参考，可选择更合适的实现方式。
5. 如果需要参考其他文件的代码才能决定（例如对比另一个文件的实现风格），选择 fix 并在修复阶段自行读取该文件，**不要为了索要代码片段、文件内容而 ask**——你能自己读代码。ask 只用于真正需要人来澄清意图或做出取舍的场景。
